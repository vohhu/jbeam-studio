# JBeam Studio — дизайн переработки

Дата: 2026-10-16
Репозиторий: [vohhu/jbeam-studio](https://github.com/vohhu/jbeam-studio) (приватный)
Основа: [BeamNG/Blender-JBeam-Editor](https://github.com/BeamNG/Blender-JBeam-Editor) v0.2.5 (MIT)
Второй источник идей и кода: [BeamNG/vscode-jbeam-editor](https://github.com/BeamNG/vscode-jbeam-editor) 0.5.0 (MIT)

## 1. Цель

JBeam Studio — аддон для Blender, который импортирует части и целые машины BeamNG из JBeam, даёт править их инструментами Blender, записывает правки обратно в `.jbeam`, не ломая форматирование и комментарии, и работает в связке с запущенной игрой.

Это переработка с нуля официального аддона BeamNG, который не обновлялся с августа 2024. Приоритеты по убыванию:

1. **Надёжность.** Любая стоковая или модовая машина импортируется и экспортируется без порчи файлов, а все проблемы видны пользователю.
2. **Удобный интерфейс.** Понятные панели, инструменты, проверки, встроенная документация.
3. **Связь с игрой.** Цикл «поправил в Blender → сохранил → машина в игре перезагрузилась» и сверка нашей сборки со сборкой игры.
4. **Новые инструменты редактирования.** Входят во второй релиз (раздел 11).

## 3. Что не входит в задачу

- Чтение машин прямо из zip-архивов игры и модов (виртуальная файловая система).
- Импорт и правка flexbody-мешей (`.dae`) и любой работы с Collada.
- Редактирование секций, кроме `nodes`, `beams`, `triangles`, `quads`, `hydros`, `torsionbars`, `torsionHydros`, `slidenodes` и `rails`: колёс, `pressureWheels`, `refNodes` и т. д. Ссылки на ноды в этих секциях при переименовании обновляются (раздел 6.3), но сами секции не редактируются. Гидравлику, торсионы, скользящие ноды и рельсы можно показывать, добавлять (кроме `torsionHydros`), удалять, отражать и менять у них свойства (раздел 6.1).
- Живая физика: показ позиций нод из идущей симуляции в Blender и запись их в анимацию. Встроенный сервер это умеет (`subscribe nodePositions`), но в планы это пока не входит.
- Отдельная работа над скоростью на очень больших машинах. Достаточно кэширования разбора и батчей отрисовки (разделы 5.5 и 8.2).

## 4. Исходное состояние

### 4.1. Что сломано в v0.2.5

Проверено 2026-10-16 на Blender 5.2.2 LTS и стоковом контенте BeamNG.drive 0.39 (122 машины).

1. **Аддон не устанавливается в Blender 5.x.** В Python 3.13 нет `typing.io`, а его импортируют `antlr4/Lexer.py`, `antlr4/Parser.py` и `luaparser/parser/LuaLexer.py`.
2. **С поправкой п. 1 проходят все 65 старых тестов**: 48 в `jbeam_import_modify_export` и 17 в `vehicle_import_modify_export`.
3. **Импорт машин из текущей игры молча не работает.** Аддон понимает только `slots`, а все 2299 файлов частей в игре используют `slots2`, старых `slots` нет ни одного. Импорт сообщает «Done», но загружается только корневая часть. Пример: у `pickup` (`d10_423sport_A.pc`) из 101 части в `.pc` загружена 1, нод 0, балок 0; то же у `etk800`, `vivace`, `bx`.
4. **Ошибки скрываются.** Об успехе и сбое импорта сообщает всплывающее окно, подробности уходят только в системную консоль, а п. 3 вообще ничем не сигнализируется.
5. **Три вендоренные библиотеки** (`antlr4`, `luaparser`, `multimethod`, около 70 файлов) нужны только для разбора выражений `$=`.
6. **Логика JBeam перемешана с `bpy` и `bmesh`** (`export_utils.py`, 1265 строк), поэтому её нельзя протестировать без Blender. Синхронизация построена на таймерах с опросом раз в 0.1 с и колбэках depsgraph на каждое изменение. Интерфейс, операторы и отрисовка лежат в одном `__init__.py` на 1171 строку.

### 4.2. Что уже есть у BeamNG

- **Расширение для VS Code** (MIT, активно развивается, последний коммит 2026-08-25). Собственный парсер SJSON с позициями, table schema, переменные (`$components`, `$.name`, `$>>components.path`, переменные слотов), выражения, проверки (дубли балок, вырожденные треугольники, ошибки таблиц и слотов, повторяющиеся ключи), словарь документации на 75 ключей, поиск плоскостей симметрии, 3D-превью на three.js. Чего оно не умеет: идти по цепочке слотов и собирать машину по `.pc` (это прямо указано в его README).
- **Встроенный сервер игры** `networking_editorToolchain` (порт 7000), который использует расширение для VS Code. Подробности в разделе 9.1.

## 5. Архитектура

### 5.1. Слои и правило зависимостей

```
ui  →  blender  →  core
```

- `core` не импортирует `bpy`, `bmesh`, `gpu`, `mathutils` и вообще ничего из Blender.
- `blender` — единственный слой, который читает и пишет данные Blender (меши, атрибуты, сцену) и регистрирует таймеры и обработчики.
- `ui` вызывает только `blender`.
- `jbeam_studio/__init__.py` импортирует `bpy`-зависимые модули только внутри `register()` и `unregister()`, поэтому `jbeam_studio.core` импортируется в обычном Python.
- Все импорты внутри пакета относительные (требование формата Extensions: пакет загружается как `bl_ext.<repo>.jbeam_studio`).
- Сторонних зависимостей и вендоренного кода нет.

Правило проверяется тестом: `tests/core` запускается в обычном CPython без Blender, а отдельный тест обходит `jbeam_studio/core` и падает, если найдёт импорт из Blender.

### 5.3. Источники кода и эталон поведения

**Код, который можно переносить.** Оба проекта BeamNG выпущены под MIT. Их логику можно переносить на Python, сохранив строки копирайта в `LICENSE` (раздел 14):

- старый аддон (`legacy/jbeam_editor` в архиве `vohhu/jbeam-studio-old`): сборка по слотам, table schema, переменные, функции выражений;
- расширение для VS Code: `src/json/sjsonParser.js`, `tableSchema.js`, `jbeamVariables.js`, `expressionParser.js`, `expressionEvaluator.js`, `expressionEnvironment.js`, `src/docHelper.js`, `webview/nodeMirrorPlanes.js` (последнее — для релиза 2).

**Эталон поведения.** Там, где переносимого кода нет, в первую очередь для цепочки слотов, `slots2` и форматов `.pc`, поведение сверяется с Lua-кодом установленной игры:

- `lua/common/jbeam/slotSystem.lua`, `io.lua`, `variables.lua`, `expressionParser.lua`, `tableSchema.lua`, `links.lua`, `loader.lua`;
- `lua/ge/extensions/core/vehicle/partmgmt.lua` (форматы `.pc`).

Этот код распространяется под bCDDL v1.1 (лицензия BeamNG), поэтому мы его читаем и пишем свою реализацию, но не копируем в репозиторий ни целиком, ни фрагментами.

### 5.4. Ядро: SJSON без потерь (`core/sjson`)

- Поддерживается диалект SJSON, на котором написаны файлы игры (сверено с `lua/common/json.test.lua`): комментарии `//` и `/* */` (без вложенности), необязательные и висячие запятые, разделитель `:` или `=`, ключи без кавычек, числа вида `.5`, `+1`, `1e3`, `Infinity`, `-Infinity`, `1#INF00`, литералы `true`, `false`, `null`, повторяющиеся ключи (побеждает последний, о дубле выдаётся `warning`), файлы без внешних фигурных скобок. Текст после конца документа игра игнорирует, у нас это `warning`.
- Парсер строит конкретное синтаксическое дерево. Каждый узел хранит свой диапазон (смещения начала и конца) в исходном тексте, а документ хранит сам текст; пробелы, запятые и комментарии — это текст между узлами. Строка и столбец вычисляются по смещению.
- Сериализация возвращает текст документа. Инвариант: `serialize(parse(text)) == text` для любого корректного файла.
- Правка заменяет диапазон токенов и не трогает ничего за его пределами.
- Ошибка разбора даёт диагностику с позицией. Остальные файлы машины продолжают обрабатываться.

### 5.5. Ядро: модель (`core/model`)

- `Part`: имя, `slotType`, определения слотов, приведённые к структуре `slots2` (раздел 5.6), таблица `variables`, секции и ссылка на файл и узел CST.
- Таблицы JBeam (строка заголовка, строки данных и словари-модификаторы, которые действуют на последующие строки) разворачиваются в записи `Node`, `Beam`, `Triangle`, `Quad`. Каждая запись хранит итоговые свойства с учётом модификаторов и ссылку на строку-источник: файл, часть, узел CST строки и узлы CST отдельных значений.
- Строки с итоговым `disable: true` в машину не попадают, но в модели остаются (для правки и подсказок).
- Разобранные файлы кэшируются по пути, времени изменения и размеру.

### 5.6. Ядро: сборка машины (`core/assembly`)

1. **Индекс.** Все `.jbeam` в `vehicles/<model>` и `vehicles/common` сопоставляются вида «имя части → файл и часть». Части из `vehicles/<model>` приоритетнее частей из `vehicles/common`. Если одно имя части встречается дважды в одной папке, выдаётся `warning` и побеждает файл, первый по пути в алфавитном порядке. Это правило при реализации сверяется с `io.lua` и фиксируется тестом.
2. **Чтение `.pc`.**
   - Формат 2: `parts`, `vars`.
   - Формат 4 (коллекция машин, так сохраняет конфиги сама игра): массив `vehicles`. У каждой машины либо `linkedPCFile` (путь к обычному `.pc`, читается по этим же правилам), либо собственные `model`, `parts`, `vars`. Берётся первая машина; остальные (прицепы) перечисляются в диагностике `info` как не импортированные.
   - Файл без поля `format`: весь объект — это карта `slot → part`.
   - Остальные форматы: диагностика `error` «формат не поддерживается».
3. **Слоты.** Обход начинается с корневой части (`slotType == "main"`). Старые `slots` (`type`, `default`, `description`) приводятся к структуре `slots2` (`name`, `allowTypes`, `denyTypes`, `default`, `description`), так делает и игра. Если в части есть оба раздела, игра использует `slots`, а `slots2` отбрасывает; мы делаем так же и выдаём `warning`. Каждый слот получает путь в дереве (`/<id слота>/<id вложенного слота>/`).
   - Выбор части: ключ в `parts` — id слота или путь слота. Как в игре, сначала ищется id, затем путь (игра пишет путь, когда id повторяется в разных ветках). Если ключа нет, берётся `default`. `""` и `"none"` (по id) означают пустой слот.
   - Если выбранная часть не найдена или не проходит `allowTypes`/`denyTypes`, выдаётся `warning` и берётся `default`. Часть из `default` игра на совместимость не проверяет, мы тоже; если её нет, слот остаётся пустым с `warning`.
4. **Переменные и выражения.**
   - Умолчания из таблиц `variables` частей перекрываются `vars` из `.pc`.
   - Поддерживаются `$name`, `$=выражение`, `$.name`, `$>>components.path`, `$components` и переменные, передаваемые через `slots2`. Семантика переносится из `jbeamVariables.js` и сверяется с `variables.lua`.
   - Выражения `$=` вычисляются собственным парсером (токенизатор и разбор по приоритетам) с тем же набором операторов и функций, что в игре. Произвольный код не исполняется: вычислитель знает только операторы и функции из этого набора.
5. **Слияние.** Секции выбранных частей объединяются в машину. У каждой ноды и балки известна часть-владелец. Ссылки балок, треугольников и квадов на несуществующие ноды попадают в диагностику.

Результат — `AssembledVehicle`: дерево слотов с путями и выбранными частями, ноды, балки, треугольники, квады, итоговые переменные и `DiagnosticList`.

### 5.7. Диагностика

Ядро не прерывает работу на первой ошибке. Каждая проблема — это `Diagnostic` с серьёзностью (`error`, `warning`, `info`), категорией (`parse`, `table`, `slots`, `variables`, `references`, `checks`, `game-diff`), файлом, строкой, столбцом и текстом. Машина собирается частично, насколько возможно. Очевидно сломанный результат тоже проверяется: если в машине ноль нод при непустом `.pc`, выдаётся `error`.

У части проблем есть `fix`: вид исправления и его аргументы, которые применяет `core/edit/fixes.py` одной правкой истории. `mark_optional` (смещение строки, которая ссылается на недостающую запись) ставит строке `"optional": true`: в объект параметров строки, новым объектом после последней колонки или, для строки короче заголовка, парой модификаторов `{"optional":true}` … `{"optional":false}` вокруг неё. Такие строки не удаляются: нода может прийти из части другой конфигурации или из мода, которого аддон не видит, а с `optional` игра пропускает строку молча и использует её, когда нода есть. `delete_duplicate` (смещение строки-повтора) удаляет строку. Оба вида выполняет `EditSession.change_rows` одной правкой по одному снимку текста; проверяется, что секции меняются ровно на удалённые записи, а предупреждений о недостающих записях становится меньше ровно на помеченные строки. `add_resets` (часть) добавляет сбросы. В режиме одной части у предупреждения о ненайденной ноде исправления нет: аддон не отличает отсутствующую ноду от ноды машины или мода, который он не видит; строки с `optional` о ней не предупреждают.

### 5.8. Проверки (`core/checks`)

Запускаются после каждой сборки и после каждого пакета операций. Правила и тексты сообщений переносятся из `tableSchema.js` расширения для VS Code там, где они там есть.

| Проверка | Серьёзность |
|---|---|
| Неверный заголовок таблицы (не список, нет заголовка) | `error` |
| Строка-модификатор, которая не является словарём | `error` |
| Строке не хватает аргументов из заголовка | `warning` |
| Дубль балки: та же неупорядоченная пара нод (правило переносится из `tableSchema.js`) | `warning` |
| Вырожденный треугольник или квад: совпадают хотя бы две ноды | `error` |
| Слоты: нет заголовка, нет `name`, `allowTypes` не список, имя слота повторяется, часть определяет и `slots`, и `slots2` | `error` / `warning` как в `tableSchema.js` |
| Повторяющийся ключ в словаре | `warning` |
| Выражение не вычисляется | `warning` |

Проверки симметрии нет: ноды с зеркальными именами (`l`↔`r`) часто несимметричны намеренно, и такие предупреждения оказались шумом.

## 6. Правки и запись (`core/edit`)

### 6.1. Операции

Набор операций релиза 1:

- `MoveNode`, `RenameNode`, `AddNode`, `DeleteNode`
- `AddBeam`, `DeleteBeam`
- `AddTriangle`, `DeleteTriangle`, `AddQuad`, `DeleteQuad`, `FlipFace`
- `SetProperty`: назначить ключу значение у набора нод или балок; используется пакетным редактированием в релизе 2
- `add_extras`, `add_rail`, `delete_extras`: гидравлика (`hydros`), торсионы (`torsionbars`), скользящие ноды (`slidenodes`) и рельсы (`rails` объектом или таблица `rails2`). Сборка складывает их в `AssembledVehicle.extras` (`ExtraEntry`: секция, ноды по порядку, имя рельса), вместе с `torsionHydros`. В меше их нет. Добавление и удаление проверяется по размеру своей секции, удаление рельса забирает его скользящие ноды. `set_property` меняет и их: строки таблиц — как у балок, рельс в объекте `rails` — своими членами. Новая скользящая нода берёт остальные ячейки из полной строки своей таблицы, если такая есть. Зеркало (`mirror`) копирует гидравлику, торсионы и скользящие ноды через `copy_extras`: строка-копия встаёт сразу после оригинала, сохраняя модификаторы над ним, ячейки и параметры строки, с отражёнными нодами. Рельс получает отражённое имя (`boxside_R` → `boxside_L`), а скользящая нода — отражённый рельс. Существующая пара узнаётся без учёта порядка нод у гидравлики, у торсиона — без учёта порядка внутри оси (2-я и 3-я ноды) и внутри крыльев (1-я и 4-я). Запись, которая соединила бы ноду саму с собой, пропускается

Каждая операция перед применением проверяется по собранной модели:

- нельзя переименовать ноду в уже занятый id;
- нельзя добавить балку на несуществующие ноды;
- при удалении ноды, на которую ссылаются балки, треугольники или квады, операция возвращает список зависимых элементов, и интерфейс спрашивает, удалить ли их вместе с нодой. Строки других секций (`refNodes`, гидравлика и т. п.), ссылающиеся на удалённую ноду, остаются в тексте; игра их отбрасывает, и операция сообщает, какие секции это затронуло;
- если строка задаёт сразу несколько элементов (часть стоит в нескольких слотах, например с префиксами `$.`), правка этой строки или добавление строки в такую часть требует явного подтверждения: иначе изменятся все экземпляры;
- ноду, чей id собирается из переменных слота (`"$.a"`), нельзя переименовать как значение — её переименовывают в тексте;
- если модификаторы ноды не позволяют поставить её в нужную точку (например, `nodeOffset` по X не пускает ноду ближе к центру, чем само смещение), операция отказывает с объяснением;
- если нода определена в нескольких частях (более поздняя часть переопределяет её), переименование и удаление затрагивают все определения.

### 6.2. Применение к тексту

- **Перемещение.** Режим выбирается переключателем в панели и запоминается в настройках аддона.
  - **«Перезаписывать координаты»** (по умолчанию). В `posX`, `posY`, `posZ` записываются обычные числа, при которых нода в игре окажется ровно там, где её поставили в Blender. Если на ноду не действуют модификаторы (`nodeOffset`, `nodeMove`, `nodeRotate`, в том числе пришедшие из опций слота), записанное число совпадает с координатой во вьюпорте. Если действуют, записывается значение до модификаторов, а панель «Выделение» показывает оба числа: итоговое и записанное в файл. Координата, заданная выражением `$=` или переменной `$name`, заменяется числом; об этом выдаётся `info` с прежним текстом, чтобы его можно было вернуть.
  - **«Сохранять выражения».** Смещение ноды прибавляется к числу в строке-источнике. Если координата задана выражением или переменной, смещение дописывается в выражение (`"$=<исходное выражение> + <смещение>"`; переменная превращается в `"$=$name + <смещение>"`). Если выражение уже заканчивается числовым слагаемым, которое добавил редактор, меняется это слагаемое, а не дописывается новое.
  - В обоих режимах число записывается с тем же количеством знаков после запятой, что было в исходнике, но не меньше трёх.
- **Добавление.** Новая строка вставляется в конец таблицы нужной секции активной части с отступами и выравниванием столбцов как у соседних строк. Если секции в части нет, она создаётся с заголовком по умолчанию.
- **Удаление.** Удаляется строка таблицы вместе с её trivia. Модификаторы, после которых не осталось строк данных, не трогаются.
- **id новой ноды.** Префикс задаётся в панели (по умолчанию `n`), номер — первый свободный во всей машине.

### 6.3. Ссылки на ноды при переименовании

Ссылки на ноды определяются по тому же правилу, что в `links.lua` игры: ссылкой считается значение под ключом, содержащим `:`.

- Столбец таблицы с двоеточием в заголовке: `id1:`, `id2:`, `id3:`, `node1:`, `node2:`, `nodeArm:` и любые другие.
- Ключ вида `"имя:"` или `"имя:секция"`, значение которого — список id. Пример: `"torqueReactionNodes:": ["e1l", "e2l"]`.
- После двоеточия может стоять имя секции. Пустое имя означает `nodes`. Переименование ноды затрагивает только ссылки на секцию `nodes`.

Переименование правит такие ссылки во всех частях машины. Остальные строки, точно совпадающие со старым id, возвращаются списком, и интерфейс показывает их на подтверждение. Старый аддон в этом месте менял любую совпавшую строку.

### 6.4. Транзакции и сохранение

- Операция может затронуть несколько файлов. Все изменения применяются в памяти атомарно: при ошибке не применяется ни одно.
- На диск файлы пишутся только по команде «Сохранить»: запись во временный файл в той же папке, затем атомарное переименование.
- При первом сохранении файла в сессии рядом создаётся копия `<имя>.jbeam.bak`, если её ещё нет.
- Сессия читает каждый файл один раз и дальше работает только с этим текстом и этим набором файлов; правки никогда не смешиваются с изменениями, сделанными снаружи. Новые JBeam-файлы, появившиеся на диске, сообщаются отдельно и подхватываются по команде «Пересканировать». Перед записью время изменения и содержимое файла на диске сверяются с прочитанным (или последним сохранённым) текстом. Если файл изменили снаружи, пользователь выбирает: перезагрузить его (несохранённые правки этого файла пропадут) или перезаписать.
- Все файлы сначала пишутся во временные (с `fsync`), и только потом переносятся на место; при сбое временные файлы удаляются.
- Отмена после сохранения возвращает прежний текст, и файл снова становится несохранённым.

### 6.5. История

У каждой операции есть обратная. История (стек операций и текущая позиция) хранится в ядре для каждой сессии.

### 6.6. Проверка записи

После каждой операции изменённый текст разбирается заново:

1. собранная модель совпадает с ожидаемой: результат конкретной операции (например, нода стоит в нужной точке с точностью до округления) и общий инвариант — размер каждой секции меняется ровно так, как предполагает операция (с учётом частей, стоящих в нескольких слотах), а остальные ноды не сдвинулись;
2. правка затрагивает только то, ради чего она сделана: каждая текстовая замена называет свой целевой узел (ячейку, строку, таблицу, часть) и может менять текст только внутри него или удалять его вместе с окружающими пробелами, запятыми и комментариями.

Переименование возвращает список прочих совпадений; `rename_preview` показывает их заранее, а выбранные пользователем места передаются в переименование и перед заменой сверяются с текущим текстом.

В режиме разработки нарушение — исключение, у пользователя — ошибка в диагностике с откатом операции.

## 7. Мост с Blender (`blender/`)

### 7.1. Представление в сцене

- **Коллекции.** Всё лежит в коллекции `JBeam`, в ней — коллекция на каждый файл `.jbeam` с объектами его частей. Машина по `.pc` получает свои коллекции файлов (у двух машин с одним файлом позиции нод разные); части, импортированные по одной, делят коллекцию своего файла.
- **Импорт машины по `.pc`.** Объект на каждую часть, у которой есть ноды или строки балок, граней, гидравлики, рельсов. Все объекты машины — виды одной сессии правки (`Group` в `blender/sessions.py`). Объект части показывает её ноды, балки и грани (по строке в этой части) и как неизменяемые оранжевые «призраки» — ноды других частей, к которым они идут; переключатель «Все ноды машины» показывает призраками все ноды, чтобы цеплять к ним новые балки. Новое из объекта части идёт в эту часть, удалить можно только её ноды и строки, призраки не двигаются.
- **Согласованность частей.** Все объекты машины всегда показывают одно состояние сессии: после любой правки остальные объекты строятся заново (часть, которая выглядит так же, только получает номер состояния). Части, открытые в Edit Mode вместе, применяются одним проходом, а после undo ведёт часть в Edit Mode или активный объект, и остальные подстраиваются под неё. Призрак, чьей ноды больше нет, не становится новой нодой.
- **Импорт одиночного `.jbeam` без `.pc`.** Объект на выбранную часть, со своей сессией. Ноды из других частей, на которые ссылаются балки этой части, показываются призраками.
- **Объекты прежних версий.** Объект всей машины из `.blend` прежних версий (без части) открывается как раньше: часть `None` в `MeshLink.build` и `plan` значит вся машина.
- **Uid.** Логика соответствия меша и сессии живёт в `core/mesh_sync.py` (без Blender, проверяется в CI). Каждая нода, группа балок между одной парой нод и группа граней на одном наборе нод получают uid. Uid не меняется, пока история ядра ходит назад и вперёд, и переживает переименование. Меш не может хранить дубли, поэтому несколько балок между одной парой нод показываются одним ребром, и удаление ребра удаляет их все.
- **Атрибуты меша.**
  - `jbs_node_uid` и `jbs_node_check` (вершины, int). Второе значение — функция uid: инструменты, которые смешивают данные вершин (подразделение ребра), дают новой вершине среднее соседних uid, а проверочное значение тогда не совпадает.
  - `jbs_beam_uid` (рёбра, int): uid группы балок; `-2` — ребро, которое есть только у треугольника или квада и балкой не является.
  - `jbs_face_uid` (грани, int), `jbs_part` (вершины, индекс части), `jbs_ghost` (вершины, нода другой части).
  - `jbs_rev` (вершины, int): номер состояния сессии, из которого построен меш (раздел 7.3).

### 7.2. Обнаружение правок

Сессия всегда приводится к тому, что показывает меш: состояние, из которого меш построен, плюс правки меша (`sessions.mirror`). Это делается через 0.3 с после каждой операции в режиме редактирования, когда инструмент (например, перемещение) закончил работу (переключатель «Применять сразу», по умолчанию включён), после каждого undo и redo, при выходе из режима редактирования (меш тогда перестраивается из сессии) и по кнопкам «Применить правки меша» и «Сохранить». Меш в режиме редактирования при этом не меняется, поэтому шаги undo Blender остаются шагами пользователя. Операторы, которые меняют сессию в режиме редактирования (переименование), сначала записывают uid и позиции результата в меш (`mesh_io.stamp`), и это попадает в их шаг undo. Все найденные изменения применяются одной операцией истории; если хоть одно нельзя применить, не применяется ничего, меш остаётся с правками, а панель показывает причину.

Сопоставление («что видишь, то и получаешь»):

- вершина с верным uid и проверочным значением — существующая нода; изменились координаты → перемещение. Оси, сдвинутые меньше чем на 0.05 мм, берутся из ядра без изменений, чтобы 32-битные координаты меша не переписывали нетронутые числа;
- любая другая вершина — новая нода в активной части (id из префикса и номера). Если uid встречается несколько раз (Shift+D, выдавливание копируют атрибуты), его сохраняет вершина с наименьшим индексом;
- ребро — балка, если его uid и концы совпадают с группой; ребро с другими концами, ребро без uid или скопированное ребро, между нодами которых балки ещё нет, — новая балка; ребро `-2` балкой не считается;
- грань из 3 или 4 вершин — треугольник или квад по тем же правилам; обратный порядок обхода → разворот; грани больше чем с четырьмя углами отбрасываются с сообщением;
- uid из сессии, которого нет в меше → удаление ноды (вместе с её балками и гранями), балки или грани;
- ноды других частей («призраки») не правятся: их перемещение и удаление откатываются перестройкой меша.

Переименование и свойства не выводятся из меша, а задаются явными операторами.

### 7.3. Undo и redo

Работает стандартный Ctrl+Z Blender, собственных сочетаний нет. Каждое состояние истории ядра имеет номер (`MeshLink.rev`): хэш содержимого изменённых файлов и случайного числа сессии, чтобы меш из старого `.blend` не совпал с состоянием новой сессии. Номер по содержимому нужен потому, что после undo и redo правки меша применяются заново и дают ту же запись в другом месте истории; одинаковые тексты дают тот же номер и те же uid (карты uid хранятся по номеру, последние 128). Собранные машины последних состояний тоже хранятся, поэтому возврат к исходному состоянию меша не пересобирает машину. Для последних 128 состояний хранятся и тексты изменённых файлов: когда повторное применение правок меша после undo обрезало историю ядра, а redo ведёт в состояние, которое было сделано операцией ядра (отражение, переименование, применённый текст), состояние восстанавливается из этих текстов новой записью истории (`EditSession.restore`).

В режиме редактирования после применения правок результат сразу записывается в меш (`mesh_io.stamp`: uid, проверочные значения, позиции, номер состояния), поэтому новые ноды сразу видны в подписях и подсветке текста. Шаг undo Blender при этом хранит меш таким, каким его оставил пользователь; переход к нему применяет те же правки и даёт то же состояние. Номер, из которого построен меш, записан в атрибут `jbs_rev` каждой вершины, поэтому Blender восстанавливает его вместе с мешем и в объектном режиме, и в режиме редактирования. Обработчики `undo_post` и `redo_post` читают номер и переводят ядро в это состояние одним `goto` (одна пересборка). Если такого состояния в истории уже нет, меш помечается устаревшим: правки из него не применяются, панель предлагает перестроить меш.

После применения правок при выходе из режима редактирования мост перестраивает меш и делает `undo_push`. Операторы (переименование, применение текста) меняют ядро и номер в меше в том же шаге undo, что и сам оператор. Проверено в окне Blender 5.2: правка, Tab, Ctrl+Z, Ctrl+Shift+Z.

### 7.4. Текстовый вид

Текст части можно открыть в текстовом редакторе Blender. Показывается текущее содержимое документа в памяти, включая несохранённые правки. Если пользователь изменил текст, в панели появляется кнопка «Применить текст»: текст разбирается, документ заменяется (это одна операция истории), машина пересобирается, меш перестраивается. Ошибки разбора уходят в диагностику, и документ тогда не заменяется.

Подсветка JBeam в текстовом редакторе (`ui/text_syntax.py`). У Blender нет формата подсветки для JBeam и нет способа добавить свой, поэтому текст рисуется редактором как обычный, а модуль перекрашивает каждый токен (`core/sjson/tokens.py`: части, секции, ключи, строки, переменные, выражения, числа, литералы, комментарии): закрашивает ячейку символа цветом, который ей дал Blender (фон, выделение, текущая строка), и рисует символ моноширинным шрифтом редактора по тем же метрикам (`TXT_LINE_HEIGHT`, `lheight_px`, `cwidth_px` из `text_draw.cc`). Проблемы разбора (по мере набора) и, пока текст совпадает с сессией, проблемы сборки подчёркиваются, отмечаются у номера строки и пишутся после строки; проблема строки курсора — в нижней строке редактора. Тексты до 200 тыс. символов разбираются сразу, длиннее — после паузы 0.4 с.

### 7.5. Внешние изменения

Таймер раз в 2 с проверяет время изменения только загруженных файлов. Если файл изменился на диске, панель показывает предупреждение с кнопкой «Перезагрузить». Если у этого файла есть несохранённые правки, кнопка спрашивает подтверждение.

### 7.6. Сохранение в `.blend`

В свойствах объекта (`Object.jbs`) хранятся путь к `.pc` (или к `.jbeam` и имя части), дополнительные папки `vehicles` и настройки правки. Копия объекта (Shift+D) с файлами не связана и предлагает стать обычным мешем. Обработчик `load_post` собирает машину заново с диска и перестраивает меш из собранной модели. Несохранённые в `.jbeam` правки при этом теряются. Поэтому при сохранении `.blend`, когда есть несохранённые JBeam-файлы, интерфейс предупреждает об этом и предлагает сначала сохранить их.

## 8. Интерфейс (`ui/`)

### 8.1. Панель «JBeam» в боковой панели 3D-вьюпорта

- **Машина:** открытый `.pc` или `.jbeam`, активная часть, список частей с переключением видимости и фильтром по имени, кнопки «Синхронизировать» и «Сохранить», число файлов с несохранёнными правками.
- **Выделение:** id и итоговые свойства выделенных нод и балок; если значение задано выражением или переменной, рядом показывается исходная форма. У каждого ключа, для которого есть документация, — подсказка и кнопка «?» (раздел 8.4).
- **Инструменты:** переименование одной ноды и пакетное переименование (префикс, суффикс, начальный номер), добавление балки, треугольника или квада из выделения, разворот граней, префикс id новых нод.
- **Диагностика:** список ошибок, предупреждений и сообщений с фильтром по серьёзности и категории. Клик по строке выделяет связанный элемент во вьюпорте, если он есть, и открывает файл в текстовом редакторе на нужной строке.
- **Игра:** раздел 9.4.
- **Вид:** подписи id нод (все, выделенные, выключены), цвета балок по типу (обычные, `|SUPPORT`, `|BOUNDED`, `|ANISOTROPIC`, `|PRESSURED`, `|LBEAM`, `|HYDRO`), полупрозрачная заливка треугольников и квадов, скрытие треугольников и квадов, отображение «призраков».

Импорт: `File > Import > JBeam Part (.jbeam)` и `File > Import > JBeam Vehicle (.pc)`.

### 8.2. Отрисовка

Отрисовка идёт через модуль `gpu`, батчи кэшируются и перестраиваются только при изменении данных сессии или видимости, а не на каждом кадре. Подписи рисуются через `blf` только для видимых в регионе нод.

Гидравлика, торсионы и рельсы рисуются линиями своих цветов, а скользящие ноды — точками, по текущим позициям вершин меша; при перетаскивании нод линии следуют за ними. Количество каждого вида показано в легенде.

**Видимость за гранями.** Цветные балки и ноды, гидравлика, рельсы, призраки и подписи скрываются за гранями, кроме X-ray, каркаса и переключателя «Сквозь грани» в шапке 3D-вида. Линии и точки рисуются с проверкой глубины сцены и чуть сдвинуты к камере (0,2 % расстояния), чтобы не мерцать на своих гранях. `blf` проверку глубины не делает, поэтому подписи проверяются отдельно: в Blender 5 — по буферу глубины, прочитанному в `POST_VIEW`, в Blender 4.5 (там скрипт получает глубину другого буфера) — лучом к ноде через `BVHTree` граней JBeam-объектов; подпись прячется, если грань ближе ноды больше чем на 1,5 % расстояния. Центр масс рисуется поверх всего.

**Цвета по значению.** Балки — по `beamSpring`, `beamDamp`, `beamDeform`, `beamStrength`, ноды — по `nodeWeight`, градиентом от синего к красному. Значение, которого нет в строке, берётся из `options` машины или из умолчаний игры (`core/physics.py`, как `loader.lua`). Шкала — от 5-го до 95-го процентиля конечных значений, логарифмическая по положительным, если они различаются больше чем в 20 раз; бесконечные (`FLT_MAX`) — отдельным цветом. Масса машины, части и выделения — сумма `nodeWeight`, без колёс, которые игра добавляет сама.

### 8.3. Языки

Строки интерфейса на английском. Русский перевод регистрируется через `bpy.app.translations` и включается автоматически при русском языке интерфейса Blender. Тексты документации (раздел 8.4) остаются на английском, как в источнике.

### 8.4. Встроенная документация

`core/docs.py` — словарь вида `"<секция> > <ключ>"` → описание, тип, значение по умолчанию, ссылка на documentation.beamng.com. Начальное содержимое — 75 записей из `src/docHelper.js` расширения для VS Code (`nodes`, `beams`, `flexbodies`, `slots`, `slots2`). Описание показывается подсказкой у ключа в разделе «Выделение», кнопка «?» открывает ссылку в браузере.

## 9. Связь с игрой

### 9.1. Встроенный сервер игры

Расширение игры `networking_editorToolchain` (есть в BeamNG.drive 0.39, мод не нужен) слушает TCP-порт 7000. Кадр: 4 байта `BN01`, длина uint32 little-endian (длина JSON плюс 1), JSON в UTF-8, байт `\0`. Если в запросе есть поле `context`, сервер возвращает его в ответе.

Сервер запускается по требованию. В Windows клиент пишет строку `beamng:v1/startToolchainServer` в именованный канал `\\.\pipe\BEAMNGCOMMANDLISTENER` и подключается через 0.5 с. В Linux канала нет, клиент просто подключается к порту.

Используемые команды:

| Запрос | Ответ |
|---|---|
| `{"cmd":"ping"}` | `{"cmd":"pong"}` |
| `{"cmd":"init"}` | `{"cmd":"siminfo","data":{versiond, root, userpath, ...}}` |
| `{"cmd":"getPlayerVehicleInfo"}` | `{"cmd":"playerVehicleInfo","data":{"jbeam": модель, "partConfig": путь к .pc или сериализованный конфиг}}` или `{"cmd":"noPlayerVehicle"}` |
| `{"cmd":"selectNodes","nodes":[id, ...]}` | без ответа; игра рисует выбранные ноды сферами с подписями |

### 9.2. Мод JBeam Studio Bridge

Наш собственный мод (MIT) для того, чего встроенный сервер не умеет. Исходники лежат в `game_mod/`, собранный `jbeam_studio_bridge.zip` входит в пакет аддона.

- `scripts/jbeam_studio_bridge/modScript.lua` загружает расширение `jbeamStudioBridge` и вызывает `setExtensionUnloadMode(..., "manual")`.
- `lua/ge/extensions/jbeamStudioBridge.lua` поднимает сервер на порту 7001 через модуль игры `require('tcpServer')`. Формат кадра тот же, что в разделе 9.1.
- Мод принимает только команды из таблицы ниже. Он не исполняет присланный код и не пишет файлы.

| Запрос | Ответ |
|---|---|
| `{"cmd":"hello"}` | `{"cmd":"hello","protocol":1,"modVersion":"...","features":[...]}` — `features` перечисляет команды, для которых нашлись нужные функции игры |
| `{"cmd":"reloadVehicle"}` | `{"cmd":"reloaded"}` после вызова `core_vehicle_manager.reloadVehicle(0)` или `{"cmd":"error","message":...}` |
| `{"cmd":"getVehicleConfig"}` | `{"cmd":"vehicleConfig","model":...,"parts":{...},"vars":{...}}` — текущий конфиг машины игрока, включая изменения, сделанные в игре. Дерево частей игры сворачивается в `parts` по тому же правилу, что в формате 4: id слота, а при совпадении id — путь слота |
| `{"cmd":"getVehicleData"}` | `{"cmd":"vehicleData","model":...,"nodes":{id:[x,y,z]},"beams":[[id1,id2],...],"triangles":[[id1,id2,id3],...]}` — машина в том виде, как её собрала игра, в координатах JBeam |

Мод проверяет наличие нужных функций игры при загрузке. Если функции нет (например, после обновления игры), соответствующая команда исключается из `features`, а запрос на неё возвращает `error`.

Установка: кнопка «Установить мод» копирует `jbeam_studio_bridge.zip` в `<userpath>/mods/`. `userpath` берётся из ответа `init`, если игра подключена, иначе из настроек аддона. По умолчанию в Windows это `%LOCALAPPDATA%\BeamNG\BeamNG.drive\current`. Игру после установки нужно перезапустить, и интерфейс говорит об этом.

### 9.3. Клиент

- `core/live/protocol.py`: упаковка и разбор кадров (в том числе склейка кадров, пришедших частями, и несколько кадров в одном чтении; неверный заголовок сбрасывает буфер с диагностикой), типы сообщений.
- `core/live/client.py`: неблокирующий клиент с состояниями `disabled → waking → connecting → connected`. Метод `poll()` читает и пишет без ожидания, вызывается снаружи. Переподключение с паузой 1, 2, 4, 6, 6… с. Клиент держит два соединения: со встроенным сервером (7000) и с модом (7001). Отсутствие мода — нормальное состояние, а не ошибка.
- `blender/live_link.py`: пока связь включена, таймер `bpy.app.timers` раз в 0.1 с вызывает `poll()` и передаёт события интерфейсу. Интерфейс никогда не ждёт игру.
- Связь включается переключателем в панели. По умолчанию выключена, состояние запоминается в настройках аддона.

### 9.4. Возможности в Blender (раздел «Игра» панели)

1. **Статус:** выключено / подключение / подключено (версия игры), установлен ли мод и какие команды он поддерживает.
2. **Папки.** После `init` в список папок с машинами в настройках аддона автоматически добавляются `<userpath>/mods/unpacked/*/vehicles` и `<userpath>/vehicles`, если они существуют.
3. **«Импорт текущей машины».**
   - Конфиг: если мод подключён — `getVehicleConfig`; иначе, если `partConfig` — путь к `.pc`, читается этот файл; иначе диагностика «конфиг изменён в игре, для его импорта нужен мод JBeam Studio Bridge».
   - Папка модели ищется по порядку: `<userpath>/mods/unpacked/*/vehicles/<model>` (моды по алфавиту), `<userpath>/vehicles/<model>`, затем папки из настроек. `vehicles/common` ищется в том же порядке. Если модели нет в распакованном виде, выдаётся диагностика с подсказкой про утилиту распаковки (раздел 10).
4. **Подсветка в игре.** При изменении выделения в режиме редактирования (с задержкой 0.2 с) id выделенных нод, не больше 1000, отправляются командой `selectNodes`. Переключатель, по умолчанию включён.
5. **Горячая перезагрузка.** После успешного «Сохранить», если мод подключён, вызывается `reloadVehicle`. Переключатель, по умолчанию включён. Если сохранённые файлы лежат вне `<userpath>`, перезагрузка не выполняется и показывается `info`: игра не видит эти файлы.
6. **«Сравнить с игрой».** `getVehicleData` сравнивается с нашей сборкой: ноды по id (есть только у нас, есть только в игре, позиция расходится больше чем на 1 мм), балки как неупорядоченные пары, треугольники как множества нод. Расхождения попадают в диагностику категории `game-diff`. Если модель в игре другая, сравнение не выполняется. Если конфиг другой, выдаётся `warning`.

## 10. Утилита распаковки

`tools/extract_vehicles.py` — замена старого `jbeam_pc_files_extractor`. Она распаковывает из всех `*.zip` указанной папки файлы `.jbeam`, `.pc` и `info.json` с сохранением путей. Запускается двумя способами: из командной строки (`--src`, `--dst`) и оператором в панели аддона (выбор папок через диалог Blender).

## 12. Тестирование

### 12.1. `tests/core` — обычный Python, CI

- GitHub Actions на Python 3.11 и 3.13.
- Фикстуры: машина `square_donut` из тестов оригинала (CC0) и новые маленькие файлы на каждый случай SJSON, таблиц, слотов, переменных, выражений, проверок и операций. Машины `agenty_legocar` и `agenty_legotrailer` из тестов оригинала — мод AgentY, они не под CC0 (это указано в `legacy/tests/vehicle_import_modify_export/vehicles/LICENSE.txt`), поэтому в новые фикстуры не берутся.
- Сценарии 65 старых тестов (ожидаемые файлы из `legacy/tests`) переносятся как приёмочные тесты операций ядра.
- `core/live`: разбор кадров (кадр частями, несколько кадров за раз, неверный заголовок) и клиент против поддельного сервера на Python, который реализует команды из разделов 9.1 и 9.2: подключение, переподключение с паузами, отсутствие мода, обрыв посреди кадра.
- Тест слоёв из раздела 5.1.

### 12.2. `tests/corpus` — контент игры, локально

Запускается, только если задана переменная окружения `JBS_VEHICLES_DIR` (папка с распакованными `vehicles`, сюда же можно подложить моды из `mods/unpacked`); иначе пропускается. В CI не запускается: файлы игры нельзя распространять.

- Без потерь: `serialize(parse(f)) == f` для каждого `.jbeam` и `.pc`.
- Сборка: каждый `.pc` каждой машины собирается без диагностик `error`, число нод больше нуля.
- Случайные правки: для каждой машины N случайных операций каждого типа (N задаётся, по умолчанию 20); после каждой выполняются проверки из раздела 6.6.

### 12.3. `tests/blender` — в Blender

- Запуск: `blender -b --factory-startup --python <runner>` с `pytest` внутри; `pytest` ставится в отдельную папку через `pip --target`, Blender не модифицируется.
- `scripts/test_blender.ps1` прогоняет набор в Blender 4.5 (портативная сборка в папке инструментов вне репозитория, путь задаётся переменной `JBS_BLENDER_45`) и Blender 5.2 (`JBS_BLENDER_52`).
- Покрытие: построение меша, обнаружение правок, undo и redo, сохранение и восстановление `.blend`, операторы импорта и сохранения на фикстурах, таймер связи с игрой против поддельного сервера.
- CI: отдельная задача скачивает портативные Linux-сборки 4.5 и 5.2 с download.blender.org, кэширует их и запускает тот же набор.

### 12.4. Ручной чек-лист

`docs/release-checklist.md` проходится перед каждым релизом: отрисовка, панели, перевод, работа с реальными машинами и связь с реальной игрой (установка мода, подключение, импорт текущей машины, подсветка, перезагрузка после сохранения, «Сравнить с игрой» на десяти машинах из раздела 11).
